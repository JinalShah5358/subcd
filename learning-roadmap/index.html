From "I can build it" to "I can architect it."

A senior-mentor plan for a working developer. You already ship React and Node. This plan closes the gaps that separate a productive developer from one who designs production systems: a real type system, real OOP, a second platform (C#/.NET), the architectural vocabulary to justify every decision you make — and, last, the engineering discipline to ship AI features that are measured rather than demonstrated.

Why this order, and not the one you proposed

You suggested OOP → TypeScript → React → Node → C# → .NET → Architecture → Projects. That is close to right. I changed three things, and here is the reasoning — you should be able to argue with it.

  1. TypeScript comes first, with OOP taught inside it. Abstract OOP theory learned in a vacuum does not stick. You use TS/JS every day, so classes, interfaces, encapsulation and SOLID can be practised on code you actually ship, this week. By the time you reach C#, OOP is muscle memory and you only have to learn syntax, not concepts. That makes the C# phase roughly twice as fast.
  2. React and Node come before C#, not after. They convert immediately into value at work, and they give you concrete reference points ("Express middleware" → "ASP.NET Core middleware", "npm" → "NuGet", "Prisma" → "EF Core"). Learning .NET as a comparison to something you know well is far faster than learning it cold.
  3. Architecture is taught twice. A light pass is embedded in the Node and .NET phases (you build layered and clean-architecture code with your hands), then Phase 7 is the formal pass where you name the patterns, compare them, and learn when not to use them. Theory after practice, so it lands on something.
  4. AI engineering comes last, and that is deliberate. Phase 9 is the one topic where learning it first actively harms you. An LLM feature is 10% model call and 90% retrieval quality, permission scoping, schema validation, cost accounting, background jobs, error handling and measurement — every one of which is taught in Phases 3 and 6. Built on top of two real systems you already secured and instrumented, the AI phase teaches engineering. Built first, on nothing, it teaches you to produce demos that cannot ship. Phases 1–8 stand alone; Phase 9 adds a capability to a foundation that is already complete.

One capstone is built mid-plan (Week 15–16) rather than all at the end. Building before you feel ready is the point: it exposes what you actually do not know, while there is still time to fix it.

Operating manual

How to use this plan

The plan only works if the daily session has a fixed shape. Improvised study time becomes tutorial-watching within a week.

The daily 2.5-hour block

0:00Recall (15 min) — close all notes. Write, from memory, what you learned yesterday and one week ago. Only then check. This single habit is worth more than an extra hour of reading.
0:15Learn (45 min) — one concept, from docs or a reference book. Not video. You are allowed video only when a concept has a visual/temporal shape (event loop, rendering, request pipeline).
1:00Build (60–75 min) — the day's exercise. Code it without copying. If you get stuck for 15 minutes, look it up, then close the tab and retype it from memory.
2:15Log (15 min) — append to NOTES.md: what → why → when to use → the mistake I nearly made. Add 1–2 interview questions to your own question bank.

On a 3-hour day, extend Build. Never extend Learn — input without output is the failure mode this plan is designed around.

Rules that make it stick

  • One repo per phase. Push every day. A commit-a-day graph is your real progress bar, not this page's checkboxes.
  • Day 6 is never new material. It is: build the mini-project, redo the week's hardest exercise from scratch, answer the interview questions aloud, take the checkpoint.
  • The "explain it" test. If you cannot explain a concept in 4 sentences to a mid-level developer, including when not to use it, you do not know it. Write the 4 sentences.
  • No tutorial without a divergence. If you follow a guide, change something deliberately — a different database, an extra requirement, stricter types. Following exactly teaches nothing.
  • Read real source. Once a week, read 30 minutes of a well-built open-source repo in that week's stack. Imitating good code is the fastest style transfer there is.
  • Do not skip a checkpoint. If you fail one, spend Day 6 of the next week on the gap. Moving on with a hole in the foundation is how people get stuck at mid-level for five years.
The realistic failure mode: weeks 1–6 feel great, week 7 gets busy at work, you miss four days, and the plan dies. Plan for it now. A missed day is skipped, not made up — you push the calendar, you never double up. And every 5th week, take Days 5–6 as pure revision if you are behind. Finishing in 48 weeks is a success; abandoning at week 8 is not. Stopping at Week 32 with the foundation complete is also a success — Phase 9 is additive, not load-bearing.

Foundations

OOP, properly

Most developers can recite the four pillars and still write procedural code in classes. The goal here is the judgement layer: knowing which relationship to model, and when a class is the wrong tool.

SOLID, with the version that is actually useful

PrincipleThe useful formThe smell it removes
SRPA module should have one reason to change — one actor who can request a change to it.A UserService that does validation, email, billing and PDF export. Four teams, one file, endless merge conflicts.
OCPAdd behaviour by adding code, not by editing a switch statement that already works.Every new payment provider means editing processPayment() and re-testing all providers.
LSPA subtype must be usable anywhere the base type is, without the caller knowing. If you need instanceof at the call site, the hierarchy is wrong.ReadOnlyRepository extends Repository that throws on save(). Classic LSP break.
ISPSmall, role-shaped interfaces. Consumers should not be forced to depend on methods they never call.An IRepository with 22 methods where every test double has to stub 22 methods.
DIPBoth the policy and the detail depend on an abstraction that the policy owns. The interface lives with the business logic, not with the database code.Your order service imports Prisma / DbContext directly, so you cannot test it or swap storage.
The senior-level caveat you must internalise: SOLID is a set of forces, not laws. Applying all five to a 40-line CRUD endpoint produces six files, three interfaces and one very confused reviewer. Apply a principle when you feel the pain it prevents — a second implementation appearing, a test you cannot write, a merge conflict that keeps recurring. "I applied DIP because I needed to test this without a database" is a senior answer. "I applied DIP because SOLID" is a junior one.
Phase 7 reference

Architectures: what, why, when

Every architecture is a trade of one kind of pain for another. The skill is not knowing the diagrams — it is knowing which pain you are currently in.

The decision guide

SituationChooseWhy
Solo dev / small team, CRUD-heavy admin app, requirements still movingLayered / MVCLowest ceremony. Do not pay abstraction tax for flexibility you will never use.
Business rules are the hard part (pricing, eligibility, scheduling, accounting)Clean / OnionRules become testable in isolation and survive framework and database changes.
One product, 3–5 teams, deployment is not the bottleneckModular monolithTeam autonomy without distributed-systems cost. The correct default for almost everyone.
Independent scaling / independent release cadence is a real, measured needMicroservicesOnly when the organisational cost is already being paid. It is an org solution first, a tech one second.
Many consumers react to the same business fact; workflows are long-runningEvent-drivenProducers stop knowing about consumers. Buy decoupling, pay in eventual consistency and debugging.
Reads and writes have wildly different shapes and loadCQRS (inside any of the above)Optimise each side separately. Not an architecture on its own — a pattern you add to one.
The question that beats every diagram: "What change do I expect to be frequent, and does this structure make that change cheap?" If the frequent change is "add a field to a form", Clean Architecture just made your life worse by requiring edits in five layers. If the frequent change is "support a second payment provider" or "the same rules, a different delivery mechanism", it just saved you.

Reference

Professional folder structures

A folder structure is a physical encoding of your architecture. If the folders do not tell a newcomer where things go, the architecture exists only in your head.

The three rules behind every good structure

  1. Organise by feature, not by technical kind. /features/orders/ beats /controllers/ /services/ /models/ the moment you have more than ~15 files, because a change request ("orders now need approval") touches one folder instead of seven.
  2. Dependencies point one way. A feature may use shared/. shared/ may never import a feature. Features should not import each other's internals — only their public index.ts. Enforce this with a linter, not with discipline.
  3. Depth is a cost. Every extra level is a tax on every future developer. Add a layer only when you can name the rule it enforces.

React + TypeScript

src/
  app/                  # composition root - wires everything, owns nothing
    router.tsx          #   route table, lazy imports, guards
    providers.tsx       #   QueryClient, Theme, Auth, ErrorBoundary nesting
    main.tsx
  features/             # the app IS this folder
    auth/
      api/              #   endpoint fns + zod response schemas
      components/       #   feature-private UI (never imported outside)
      hooks/            #   useLogin, useSession
      types.ts
      index.ts          #   PUBLIC surface. Nothing else is importable.
    orders/
      api/ components/ hooks/ utils/
      pages/            #   route-level screens for this feature
      index.ts
  components/ui/        # design system. Dumb, generic, zero business logic.
    button.tsx input.tsx dialog.tsx data-table.tsx
  hooks/                # genuinely global: useDebounce, useMediaQuery
  lib/                  # third-party wiring: axios client, queryClient, dayjs
  config/               # env.ts (zod-validated), constants, feature flags
  types/                # global.d.ts, api contracts shared across features
  styles/
  test/                 # msw handlers, render helpers, fixtures

app/ is the only place allowed to know about every feature. It is the composition root — the React equivalent of Program.cs.

features/x/index.ts is the contract. If orders needs something from auth, it imports from features/auth, never features/auth/hooks/useSession. Enforce with eslint-plugin-boundaries or an import/no-restricted-paths rule.

components/ui/ must never import from features/. If a "generic" component needs an order type, it is not generic — move it into the feature.

config/env.ts parses import.meta.env through zod at startup so a missing variable fails the build, not a user's checkout at 2am.

Node + TypeScript (modular monolith)

src/
  main.ts               # bootstrap: build container, start server, signals
  app.ts                # express app assembly, middleware order
  config/
    env.ts              #   zod-parsed process.env - throws at boot
    index.ts
  modules/
    orders/
      order.routes.ts       # HTTP shape only: path, middleware, delegate
      order.controller.ts   # req/res <-> DTO. No business logic. Ever.
      order.service.ts      # use cases + transaction boundaries
      order.repository.ts   # the ONLY file that talks to the ORM
      order.schema.ts       # zod DTOs in/out; types inferred from these
      order.types.ts        # domain types, not DB rows
      order.events.ts       # domain events this module publishes
      __tests__/
      index.ts              # public surface for other modules
    users/ billing/ notifications/
  shared/
    errors/             #   AppError, NotFoundError, ConflictError + http map
    middleware/         #   auth, rbac, validate(schema), rateLimit, errorHandler
    db/                 #   prisma client, transaction helper, migrations
    logger/             #   pino + redaction + requestId via AsyncLocalStorage
    cache/ queue/ mailer/ storage/
    utils/
  jobs/                 # BullMQ workers + schedules (separate process entry)
  types/express.d.ts    # augment Request with user, requestId, tenantId

routes → controller → service → repository is the whole discipline. Each layer may call the one below and never the one above. A controller that imports Prisma is a bug, not a shortcut.

order.schema.ts is the single source of truth: zod schema defined once, request type inferred with z.infer, validation middleware uses the same object. Types and runtime checks can never drift.

shared/errors gives you one errorHandler at the end of the middleware chain. Services throw new NotFoundError('Order', id); nothing below the handler ever touches res.status().

jobs/ has its own entry point so workers scale separately from the API. Same code, different process — this is the cheapest scaling decision you will ever make.

    Filters/ Extensions/ appsettings.json
tests/
  Atlas.Domain.UnitTests/  Atlas.Application.UnitTests/
  Atlas.Api.IntegrationTests/      # WebApplicationFactory + Testcontainers

The dependency rule is the whole point: Api → Infrastructure → Application → Domain. Never the reverse. Verify it by opening each .csproj — Atlas.Domain.csproj must have zero ProjectReference and ideally zero NuGet packages.

Interfaces live with the consumer. IOrderRepository sits in Domain (or Application); the implementation sits in Infrastructure. That inversion is what lets you test business rules with no database at all.

Behaviours/ are MediatR pipeline steps — validation, logging, transactions run for every command without a single line inside handlers. This is the .NET answer to Express middleware, applied at the use-case level instead of the HTTP level.

Api/ stays thin. A controller action should be 3 lines: build the command, send it, return the result.

Full-stack monorepo

repo/
  apps/
    web/                # React + TS (structure as above)
    api/                # Node + TS  (or /api-dotnet for the .NET version)
    worker/             # background jobs
  packages/
    shared-types/       # DTOs generated from zod / OpenAPI - one source of truth
    ui/                 # design system consumed by every frontend
    config/             # eslint, tsconfig, prettier bases
    utils/
  infra/
    docker/  docker-compose.yml
    migrations/

  docs/
    adr/                # 0001-use-modular-monolith.md, 0002-choose-postgres.md
    architecture.md     # C4 context + container diagrams

  package.json          # pnpm workspaces + turbo pipeline

packages/shared-types is the highest-leverage folder in a full-stack repo: define the API contract once, and a backend change that breaks the frontend fails at compile time instead of in production.

docs/adr/ — Architecture Decision Records. One short markdown file per significant decision: context, options, decision, consequences. Writing these is the single most senior-looking habit you can build, and it is the thing interviewers probe for when they ask "why did you choose X?".

ONBOARDING.md is your own test: if a new developer cannot go from clone to a running app in 10 minutes, your setup is too complicated, and that complexity is costing your team every single week.

AI features inside an existing app

application/
  ports/
    ILlmClient.ts           # the contract YOUR code owns. No SDK types here.
    IRetriever.ts           # search(query, scope) -> Chunk[]  - scope is mandatory
  use-cases/
    summarise-deal.ts       # depends on the ports only. Testable with a fake.
infrastructure/
  ai/
    anthropic-client.ts     # the ONLY file that imports the SDK
    tools/                  #   tool definitions + executors, one file each
    streaming.ts            #   SSE bridge to the transport layer
    cost-meter.ts           #   tokens + price per call, written to your logs
  retrieval/
    pgvector-retriever.ts   #   hybrid search; ALWAYS takes the caller's scope
    chunker.ts  embedder.ts
prompts/
  deal-summary/
    v3.md                   # versioned, reviewable, diffable artifacts
    v2.md                   #   keep old versions - rollback is a config change
evals/
  deal-summary/
    cases.jsonl             #   real traffic, not synthetic, where possible
    grader.ts               #   assertions or judge - defensible either way
    run.ts                  #   runs in CI; the score gates release
jobs/
  ingest-documents.ts       # re-index on record change, incrementally

ports/ is the whole architectural idea. ILlmClient is defined by your application layer, not by the SDK — which is exactly the rule you applied to IOrderRepository. It means a use case can be unit tested with a deterministic fake, at zero cost, with no network and no API key.

infrastructure/ai/ is the only place allowed to import the vendor SDK. If that import appears anywhere in application/ or domain/, the dependency rule has been broken and your AI logic is now untestable.

prompts/ holds prompts as files with version numbers, because a prompt is a deployable artifact with behaviour. In a handler as a string literal it cannot be diffed, reviewed, A/B tested or rolled back without a deploy.

evals/ next to the feature, running in CI. Without it, "did that prompt change help?" is unanswerable, and you will eventually ship a regression you cannot see.

The scope parameter on IRetriever is not optional by design. Making the caller's permission scope a required argument means the type system refuses to let you forget it — the same structural trick as tenant scoping in the repository layer.

Folder-structure mistakes to avoid: deep barrel files that re-export everything (they wreck tree-shaking and create import cycles); a utils/ folder that becomes a 3,000-line junk drawer — if you cannot name the file precisely, the function belongs in a feature; mirroring the backend folder tree in the frontend just because it looks tidy; and a components/ folder with 120 flat files. Also: never let a folder structure be aspirational. If half the code ignores it, it is misinformation.
Cross-cutting · starts Week 1

Developing with AI while you are still learning

This is separate from Phase 9. Phase 9 is building AI features. This is about the assistant sitting in your editor for the next 38 weeks — which, used without a rule, is the single biggest threat to this plan working.

The honest problem. Learning happens in the gap between not knowing and knowing — the fifteen uncomfortable minutes where you are stuck. An AI assistant closes that gap instantly and pleasantly, and you finish the day with working code and no new capability. It feels like the most productive you have ever been. Six months later you cannot write a reducer without it. This is not an argument against using AI; it is an argument for using it deliberately, which almost nobody does.

The rule: AI is scoped to the block

Apply it to the daily 2.5-hour block from the operating manual. The distinction is not "AI good" or "AI bad" — it is whether you are currently trying to build a capability or currently trying to get something done.

BlockAIWhy
RecallNoThe whole value is retrieval from your own memory. Checking with AI first destroys the measurement.
LearnLimitedRead the primary source first. Then AI is excellent for "explain this differently", "why does this exist", and "what would break without it".
BuildNoThis is where capability forms. Write the exercise yourself, badly, from a blank file. The 15-minute rule applies: stuck for 15 minutes, look it up in docs, close the tab, retype from memory.
ReviewYesAfter it works: "critique this like a staff engineer" is one of the highest-value prompts available to you. You get review at a level you may not have access to at work.
Everything elseYesWork code outside the topic you are learning, config, boilerplate, scripts, docs. Unrestricted — that time is not study time.

Four prompts that make you better, not weaker

  • Explain-back critique. "Here is my explanation of how the event loop handles this. Tell me what is wrong or missing, and do not be generous." You produce first; AI grades. This is the reverse of the usual flow and it is the one that builds recall.
  • Socratic mode. "Ask me five increasingly hard questions about EF Core change tracking. Do not give answers until I have attempted each." A free examiner, on demand, at whatever difficulty you need.
  • Staff-engineer review. "Review this module for correctness, security and structure. Be specific about the failure scenario for each finding." Then — and this matters — verify every finding yourself. Some will be wrong, and catching those is its own exercise.
  • Trade-off interrogation. "Argue the strongest case against this design, then the strongest case for." AI defaults to agreeing with you; forcing both sides is how you get a real second opinion instead of a mirror.
The prompt to never use during Build: "Write the solution to this exercise." You will read it, understand it, feel you have learned it, and retain nothing. Understanding someone else's solution and being able to produce one are different skills, and only the second one gets you hired or promoted.

Then: using AI as a professional, which is a real skill

Once a topic is learned, the restriction lifts entirely and a different skill takes over. Working effectively with an AI assistant is now a genuine differentiator, and "how do you use AI in your work?" is a real interview question with good and bad answers.

Where it earns its place
  • Boilerplate you have written a hundred times — CRUD scaffolding, DTO mapping, test fixtures, config
  • Exploring an unfamiliar API surface fast, then verifying against the real docs
  • Mechanical refactors and migrations across many files
  • A first-pass review before a human sees your PR
  • Turning your bullet points into an ADR, a README, or a PR description
  • Rubber-ducking a bug — often you solve it while writing the prompt
  • Test generation, after you have decided what should be tested
Where it costs you
  • Architecture decisions — it will agree with whatever you proposed, which feels like validation and is not
  • Security-critical code you cannot fully audit yourself
  • Anything in a domain where you cannot evaluate the output — you are accepting risk you cannot see
  • Large diffs. If you cannot review it line by line, you did not write it and you do not own it, but you will be on call for it
  • Library or version specifics — confidently stated, sometimes out of date. Verify against docs
  • The subtly-wrong answer that compiles, passes your tests, and fails in production. This is the expensive failure mode
The principle that governs all of it: you can only safely accept what you can review. Your review ability is the hard ceiling on how much leverage AI gives you — which means every week of this plan raises that ceiling. A developer who deeply understands transactions, RBAC and the dependency rule gets enormous value from an assistant, because they can spot the bad suggestion in two seconds. A developer who does not gets a faster way to produce code they cannot defend. Same tool, opposite outcomes, and the difference is exactly what the 38 weeks are for.

Practical habits worth adopting now: keep a rules file in each repo (CLAUDE.md, .cursorrules or equivalent) describing your conventions, folder structure and the things you never want done — it converts repeated corrections into a one-time cost. Work in small diffs you can actually read. Ask for the plan before the code on anything non-trivial. And when it produces something you would not have written, decide whether that is because it is better or because it is wrong — answering that question honestly, several times a week, is itself one of the fastest ways to improve.

Apply everything

Capstone projects

Two required, one optional. Both required projects are the same class of software — a business system with roles, money, workflow and reporting — deliberately, so the second one isolates the platform difference rather than the domain difference.

The bar both projects must clear

These are not optional polish. They are what makes the difference between a portfolio toy and evidence that you can work on production systems — and they are exactly what a technical interviewer will dig into.

  • Architecture you can defend — an ADR for every major decision, and an honest paragraph on what you would do differently at 100× the scale.
  • Auth done properly — hashed passwords (argon2/bcrypt), short-lived access tokens, rotating refresh tokens, revocation, logout-everywhere.
  • Real RBAC — a permission matrix, checks enforced on the server (the UI only hides, the API denies), and resource-ownership checks that stop user A reading user B's invoice.
  • A considered schema — normalised, indexed for the actual queries, foreign keys enforced, soft-delete and audit columns, and migrations that run in CI.
  • Validation at the boundary — one schema per endpoint, typed from the same source, with structured field-level errors the frontend can render.
  • One error contract — every failure returns the same shape with a stable machine-readable code. No stack traces to clients, no leaked internals.
  • Structured logging + correlation IDs — one request traceable end-to-end, with PII redacted.
  • Tests that would catch a regression — unit tests on business rules, integration tests on the API against a real database in a container, one E2E happy path.
  • Deployed, with a README — live URL, seeded demo accounts per role, architecture diagram, and a short "what I would improve" section.
