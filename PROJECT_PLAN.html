Non-negotiable product constraints

The extension MUST

  • Activate only on the configured IFP host, never <all_urls>.
  • Operate inside the CA's own already-authenticated browser session.
  • Fill only visible, enabled, user-editable form controls.
  • Visually mark every field it touched, and report what it could not fill.
  • Leave the final review and the submit click entirely to the human.

The extension MUST NOT

  • Click submit, call form.submit(), or dispatch a synthetic submit event.
  • Read, solve, bypass, or forward CAPTCHA content.
  • Read password fields, or store/transmit IFP credentials or session cookies.
  • Run headless, scheduled, or hidden automation of the portal.
  • Execute remotely fetched code (MV3 CSP forbids it; we also forbid it by policy).

What this document is and is not

It is an implementation-ready plan: schema, API surface, module layout, security controls, phased tasks with acceptance criteria and dependencies. A developer can pick up any task card and start.
It is not legal advice, a compliance certification, or a claim that the IFP portal's terms permit browser-assisted form filling. Items marked Legal are decisions for the firm's counsel, not engineering defaults.

System Architecture

Three deployable components share one backend. The trust boundary that matters most is between our platform (which we control) and the IFP portal (which we do not). Nothing crosses that boundary except keystroke-equivalent input typed into a form by a logged-in human's browser.

Autofill request flow (happy path)

1.  CA opens ifp.gujarat.gov.in and logs in manually (credentials + CAPTCHA, unaided).
2.  Content script matches host + path, reads the DOM, computes a form fingerprint
    (ordered hash of field name/id/type triples) -- no field VALUES are read.
3.  Content script -> service worker: { fingerprint, url, formHint }.
4.  Service worker checks it holds a valid extension access token.
    If not -> popup shows "Pair with your firm account" (pairing code flow).
5.  SW: GET /api/v1/extension/form-versions/resolve?fingerprint=...
    -> { formVersionId, matchQuality: EXACT | HEURISTIC | UNKNOWN }
6.  CA picks a case in the popup (list is scoped to their firm, server-enforced).
7.  SW: GET /api/v1/extension/cases/:caseId/autofill?formVersionId=...
    -> server assembles ONLY the fields mapped for that form version,
       applies transforms server-side, returns { fields:[{mappingId, selector[],
       value, type, required, status}], warnings:[], validation:{blocking:[]} }
    -> writes AuditLog EXTENSION_DATA_REQUESTED + opens an AutofillSession row.
8.  SW -> content script: payload (kept in memory; not written to chrome.storage).
9.  Content script resolves each selector with fallbacks, sets the value using the
    native property setter, dispatches input + change (+ blur) so the page's own
    listeners and validators run exactly as if typed.
10. Each field is outlined and badged: FILLED / MISSING_DATA / MISMATCH /
    UNSUPPORTED / SELECTOR_FAILED. Summary panel lists everything not filled.
11. CA reviews every field, fixes anything wrong, uploads files manually,
    solves CAPTCHA manually, and clicks Submit themselves.
12. Extension posts per-field outcomes back: POST /extension/autofill-sessions/:id/report
    -> AuditLog FORM_AUTOFILL_COMPLETED + AutofillFieldOutcome rows drive mapping health.
Why transforms run server-side. Date formats, dropdown code lookups and number scaling are part of the mapping contract. Keeping them on the server means a mapping fix is a database change that takes effect immediately for every installed extension — no extension release, no version skew. The content script stays a dumb, auditable filler.

Database Architecture

Isolation model

Single database, single schema, firmId discriminator on every tenant-owned table, enforced in a Prisma client extension and PostgreSQL Row Level Security. Per-tenant schemas were rejected for the MVP (migration cost scales with tenant count).

Key strategy

UUID v7 primary keys (String @id @db.Uuid), generated in the application. Time-ordered, so index locality is close to a bigserial while remaining non-enumerable in URLs.

Conventions

snake_case columns via @map, createdAt/updatedAt/createdById on mutable tables, soft delete (deletedAt) on Client/Case/Document only, hard delete everywhere else.

// src/db/tenant.ts - the ONLY way application code gets a Prisma client.
// A lint rule forbids importing the raw PrismaClient anywhere except here.

const TENANT_MODELS = new Set([
  'Client','ClientPromoter','Case','Project','Loan','Employment','Investment',
  'FirstSale','Document','CaseDocument','CaseValidationRun','CaseValidationFinding',
  'ConsentRecord','AutofillSession','AuditLog','User','Invitation',
  'RefreshToken','ExtensionDevice',
])

export function forTenant(firmId: string) {
  return basePrisma.$extends({
    query: {
      $allModels: {
        async $allOperations({ model, operation, args, query }) {
          if (!model || !TENANT_MODELS.has(model)) return query(args)

          // 1. force a firmId filter on every read/update/delete
          if (READ_OPS.has(operation) || WRITE_FILTER_OPS.has(operation)) {
            args.where = { AND: [args.where ?? {}, { firmId }] }
          }
          // 2. force firmId on every create; reject a mismatched client-supplied value
          if (CREATE_OPS.has(operation)) {
            assertNoForeignFirmId(args.data, firmId)
            args.data = injectFirmId(args.data, firmId)
          }
          // 3. raw queries are not allowed through this client at all
          return query(args)
        },
      },
    },
  })
}

// Every request runs inside a transaction that also sets the RLS variable,
// so even a bug in the extension cannot leak across tenants:
export async function withTenant<T>(firmId: string, fn: (tx: Tx) => Promise<T>) {
  return basePrisma.$transaction(async (tx) => {
    await tx.$executeRaw`SELECT set_config('app.firm_id', ${firmId}, true)`
    return fn(tx)
  })
}

API Planning

Conventions

  • Base path /api/v1; version in the path, never in a header.
  • JSON only; application/problem+json for errors.
  • Cursor pagination (?cursor=&limit=), max 100.
  • Every mutating route needs an Idempotency-Key or is naturally idempotent.
  • firmId is never a request parameter — it comes from the token.

Auth model

  • Web: access JWT (15 min) in memory + refresh cookie (httpOnly, Secure, SameSite=Lax, path-scoped to /api/v1/auth).
  • Extension: access token (15 min) in chrome.storage.session; refresh token bound to an ExtensionDevice, scope extension:* only.
  • Extension tokens can never call write endpoints outside /extension/*.

Rate limits (per user + per IP)

  • /auth/login 5/min, exponential lockout.
  • /auth/refresh 30/min.
  • /extension/* 60/min.
  • Reads 300/min, writes 120/min.
  • Document downloads 30/min.

Validation engine design

evaluate(caseId) ->
  1. load the case aggregate ONCE (single query with relation joins)
  2. resolve the active ruleset:
       rules where status=ACTIVE
         and (schemeVersionId = case.schemeVersionId OR schemeVersionId IS NULL)
         and effectiveFrom <= today and (effectiveTo is null or >= today)
  3. build a flat value map keyed by InternalField.code
       (decrypting only the sensitive fields a rule actually references)
  4. for each rule version: walk the expression AST with the allow-listed
     operator table; produce a finding when the predicate fails
  5. persist CaseValidationRun + findings, compute readinessScore
  6. return { blocking[], warnings[], info[], readinessScore, rulesetHash }

Guarantees: pure function of (case data, ruleset). No network calls, no clock
reads outside a single injected `today`, so a run is reproducible and testable.
Why the ruleset hash matters. Storing rulesetHash on the run lets us answer "was this case validated under the old rules?" after a scheme amendment — and re-run only affected cases instead of all of them.

Field fill algorithm

for each field in payload.fields sorted by fillPriority:
  if field.status != READY            -> badge(MISSING_DATA | UNSUPPORTED); continue
  el = resolve(field.selectors)        // primary, then ordered fallbacks
  if !el                               -> badge(SELECTOR_FAILED); record index; continue
  if guards.isForbidden(el)            -> badge(UNSUPPORTED); continue
      // forbidden: type=file|password|hidden, name/id ~ /captcha|otp|pass/i,
      //            disabled, readonly, aria-hidden, zero-size, outside the form
  if field.inputType == SELECT:
      opt = matchOption(el, field.value, field.optionLabel, matchStrategy)
      if !opt                          -> badge(VALIDATION_MISMATCH); continue
      setNativeValue(el, opt.value)
  else if checkbox/radio:
      setChecked(el, field.value)
  else:
      if field.validationExpr and !test(field.value) -> per onMismatch policy
      setNativeValue(el, field.value)   // Object.getOwnPropertyDescriptor(
                                        //   HTMLInputElement.prototype,'value').set
  dispatch input, change (bubbles:true); dispatch blur for date pickers
  if el.dependsOn -> await settle(250ms) before dependent fields (cascading selects)
  badge(FILLED); record outcome

afterward:
  render summary panel: filled / missing / mismatch / unsupported / failed
  assert: no submit button was clicked, no form.submit() called  (unit-tested)
  POST report (statuses only, no values)

Using the native property setter plus a bubbling input event is what makes React/Angular/ASP.NET-bound pages actually register the value, instead of the field visually changing but the page's own model staying empty. This is the single most common cause of "it filled but the portal said it was blank".

Data classification drives every control below. C3 = identity/financial identifiers (PAN, Aadhaar last-4, loan account). C2 = personal and commercial data (names, contacts, amounts, documents). C1 = operational metadata. C0 = public catalog data.

Phase 0 — IFP field mapping 1–2 weeks

Goal

Replace every assumption about the IFP form with an observed fact, recorded in a machine-readable field map. Nothing downstream is trustworthy until this exists.

Inputs required

  • Screen-share or sanitised DOM export — never the CA's credentials.

Deliverables
